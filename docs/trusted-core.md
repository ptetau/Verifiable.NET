# The Trusted Core

Verifiable.NET tells you a contract is **proved**. That claim is only as good as the code that makes it. This page explains which code that is, how it is kept apart from everything else, how we check it, and what is still taken on trust.

## Core vs utility

- **Core** is the small set of rules that turn a solver answer into a verdict. If one is wrong, Verifiable.NET can report a method with a bug as proved.
- **Utility** is code that finds, runs, formats or explains. Most of it can only produce a bad message or a crash. Some utility code can still affect a verdict; it is listed under [What is still trusted](#what-is-still-trusted-not-proved).

The core lives in [`src/Verifiable.Core`](../src/Verifiable.Core). It has no Roslyn, file, process or network access. The analyzers, the nullability suppressor and `verifiable-query` call into it for every verdict instead of keeping their own copies of these rules.

## What the core decides, and what is proved

Each rule is written as a `Spec.Ensures` contract next to the code, and Z3 checks it every time the project builds. Two tiny helpers (`IsOutstanding`, `JoinCore`) are single expressions used by the contracts and lemmas, and carry no contract of their own.

| Core function | Rule proved by Z3 |
| --- | --- |
| `ProofKernel.Decide` | An obligation is proved **if and only if** Z3 answered `unsat`. `sat` is the only way to refute. A missing solver is never a pass. |
| `ProofKernel.BuildRefutationQuery` | The build-time query is **exactly** the premises, then the path condition (if any), then the negated goal. Nothing else can be slipped in. |
| `ProofKernel.NamedNegatedGoal` | The labelled goal at the end of a `verifiable-query` script is exactly the negated goal. (The rest of that script is built by `QueryEngine`; see below.) |
| `SolverPlumbingKernel.NamedAssertion` | Each labelled premise of a `verifiable-query` script asserts exactly its formula, under its label, and nothing else. |
| `SolverPlumbingKernel.CacheKeyField`, `CacheKeyEvalEntry`, `CacheKeyMaterial` | The cache key is exactly the solver identity, mode, timeout, script and evaluated expressions, each as one length-prefixed field. The length is written as two UTF-16 code units, so a field's text can never run into the next field. |
| `Proofs/CacheKeyLaws.cs` | The cache key is one-to-one: equal keys come only from equal solver, mode, timeout, script and eval list. Two step lemmas (a field, or an eval entry, followed by more text decodes in only one way) cover the eval list one entry at a time; the induction over its length is argued, not machine-checked. |
| `ProofKernel.ClassifyStatusLine` | Only the exact token `unsat` reads as a proof. An `(error ...)` line is never ignored. |
| `ProofKernel.ReadCheckSatAnswer` | `unsat` is only reported if Z3 printed exactly `unsat` and nothing before it was another verdict or an error. Empty output is an error. |
| `ProofKernel.BlocksBuild` | Decides the severity of `VER104`: a missing solver stops the build unless the project explicitly opts out with `VerifiableAllowMissingZ3`. (Refuted and undecided obligations stop the build through the default Error severity of `VER102`/`VER103`. A project can still lower that severity; `VER107` then reports it.) |
| `ProofKernel.IsCacheable` | Only definitive answers (`unsat`, `sat`) are cached. Timeouts and errors are always retried. |
| `ProofKernel.AcceptCachedAnswer` | A cached answer replaces a Z3 call only if its signature checked out and it is a definitive `unsat` or `sat`. (The signature check itself is in `SignedAnswerCache`, which is tested, not proved.) |
| `ProofKernel.PremisesContradict` | Premises are called contradictory only when Z3 answers `unsat` to them alone; an undecided check is not evidence either way. When they contradict, the analyzer rejects the method's proofs with `VER105`. |
| `VacuityKernel.GuaranteeQuery`, `ReachabilityQuery` | The two checks of a callee guarantee are **exactly** the assumptions made before the call, then the call's context (path, guard, callee preconditions), then (first check only) the guarantee. |
| `VacuityKernel.NeedsReachabilityCheck`, `ClassifyGuarantee` | A callee guarantee is impossible at a call (`VER105`) only when Z3 answers `unsat` with the guarantee and `sat` without it. `unsat` both times is dead code, not a contradiction. An undecided check never counts as either. |
| `VacuityKernel.CheckUndecided` | Any premise-check answer other than `sat` or `unsat` leaves vacuity open and is reported (`VER106`), never treated as fine. |
| `QueryKernel.Aggregate` | One counterexample refutes a query. An undecided path blocks a proof. A proof that never used the goal is flagged as vacuous. |
| `CheckSelectionKernel.Select` | A method is passed over in silence only when it was lowered completely and has no obligations. Any obligation found goes to Z3. Code that cannot be lowered is a `VER101` error when the method has contracts or obligations, and a `VER101` warning otherwise, so an unchecked method never looks proved. |
| `SuppressionKernel` | `VER101`-`VER106` are the proof checks. Configuring one below an error (`warning`, `suggestion`, `silent`, `none`, a `#pragma`, a `[SuppressMessage]`) counts as weakening it, so `VER107` reports it. `VER107` is an error by default, so such a setting stops the build; `VerifiableAllowWeakenedProofs` turns the report into a warning for a project that weakens a check on purpose. The only exception to the weakening rule is `VER104` as a warning under `VerifiableAllowMissingZ3`. Suppressing `VER107` itself is also reported. A `[SuppressMessage]` check ID names the ID before its first `:`. |
| `ObligationLattice.Join` | When two paths merge, a `[MustConsume]` token that may be live on either path is still flagged, unless one side is a sink-method parameter (which may hold the token). A token counts as consumed only if it was consumed on both paths. |
| `Proofs/LatticeLaws.cs` | The merge is commutative, idempotent, associative and an upper bound. |
| `LinearTransfer.*` | The `VER007` per-statement rules, each with an exact contract. Consuming a token (passing it to a `[ConsumesObligation]` method, moving it or returning it) makes it consumed, and is a double consumption exactly when it was already consumed on every path. Reading a consumed token is a use after consumption. `_ = token` and overwriting a variable are reported exactly when the old token may still be live. At exit, a live token is a leak and a maybe-live one a partial-branch leak. A sink method's own parameter is never reported, unless it is overwritten. |
| `Proofs/TransferLaws.cs` | Every transfer rule is monotone and distributes over the merge, so the `VER007` worklist reaches the same fixed point in any visiting order, and that answer is the merge of what each path gives alone. A merge that changes a state raises its rank, and a rank is at most 2, which bounds how often the worklist can revisit a block. |

## How the core is checked

1. **Build.** `src/Verifiable.Core` is compiled with `[assembly: Verifiable]` and Z3 attached. A failed proof is a `VER102` build error, so `dotnet build Verifiable.NET.sln` fails if a rule is broken. This needs Z3 (see [Rules for contributors](#rules-for-contributors)). The analyzer that does this is not the one that ships. It is `Verifiable.Analyzers.Bootstrap`: the same analyzer sources, built with a frozen, earlier copy of the kernel in [`src/Verifiable.Analyzers.Bootstrap/Kernel`](../src/Verifiable.Analyzers.Bootstrap/Kernel). So a change to the live kernel is proved by the previous kernel, not by itself. This is stage-0 bootstrapping, as compilers do it.
2. **Break tests.** `KernelSelfVerificationTests` re-runs the proof on the kernel sources, then breaks the kernel on purpose, one rule at a time, and checks each break is rejected. This shows the contracts are strong enough to catch the bugs they exist for.
3. **Independent checks.** If the analyzer that proves the kernel were built from that same kernel, a kernel bug that blinded the prover would approve itself. For example, an extra `(assert false)` in `BuildRefutationQuery` makes every query `unsat`, including the query for its own contract. With the bootstrap, the frozen kernel builds those queries, so that bug fails the `Verifiable.Core` build with `VER102`. Three checks do not depend on the live kernel's prover:
   - The bootstrap build above. `BootstrapKernelTests` loads the same bootstrap DLL, checks that it proves the live kernel and rejects the `(assert false)` bug, and writes which kernel files differ from the frozen copy to the test output.
   - `Verifiable.Core.Tests` runs the compiled kernel against simple reference implementations, exhaustively for the small enums and with GalaxyCheck for strings and output lines. It needs no Z3.
   - Canary tests (`KernelSelfVerificationTests.Canary_*`, `BootstrapKernelTests.Canary_*` and the wider analyzer suite) require each analyzer as built to reject contracts that are plainly false.

   The bootstrap separates only the kernel. Both analyzers share the C# to SMT translation, so a translation bug that hid a goal would still pass the kernel's own proof (see [What is still trusted](#what-is-still-trusted-not-proved)). And a bug that is in the frozen copy too, because it was promoted, is caught only by the tests.

## How the proved code ships

`Verifiable.Analyzers` compiles the same kernel `.cs` files into its own DLL (see `Verifiable.Analyzers.csproj`). The analyzer targets `netstandard2.0` and cannot reference `Verifiable.Contracts`, so the kernel's `Spec.*` calls bind to a small stand-in (`KernelShim.cs`). They are `[Conditional]` and removed from the compiled code, just as in user code. Every kernel file ships except `AssemblyInfo.cs` and the `Proofs/` lemmas. The bootstrap analyzer and its frozen kernel are never packed: `Verifiable.Analyzers` and `Verifiable.NET` ship the analyzer built from the live kernel.

## What is still trusted, not proved

The core is small on purpose. These parts are outside it and are trusted:

- **Z3** gives correct `sat`/`unsat` answers.
- **Roslyn** gives a correct control-flow graph and types.
- **The C# to SMT translation** (`CfgSsaLowerer` and friends) turns your code and contracts into formulas that mean the same thing. This is the largest trusted part. It is covered by tests, not by proof. Besides the example tests, a differential suite (`TranslationValidationProperties`) generates small random methods and runs them on the CLR. With the inputs pinned by `Spec.Requires`, the analyzer must then prove the result the CLR returned, refute any other result, and refute a `DivisionByZero` or `Overflow` obligation exactly when the CLR threw. This runs in all three arithmetic modes: the default (overflow must not happen, so the analyzer must refute an `Overflow` obligation exactly when the CLR's `checked` run threw), `[CheckedArithmetic]` (bit-vectors, same rule), and `[UncheckedArithmetic]` (integers wrap, so the values must agree with the CLR even where the arithmetic overflows).
  - **Covered:** `int` and `long`, by default, with `[CheckedArithmetic]` and with `[UncheckedArithmetic]`; `+ - * / %` with negative operands and edge values such as `MinValue`; unary minus, comparisons, `&& || !` and `?:`; `Math.Abs`, `Math.Min` and `Math.Max`; the bit operators `~ & | ^ << >>`, casts that wrap through `byte`, `sbyte`, `short`, `ushort`, `char`, `int`, `uint` and `ulong`, and compound assignment and `++`/`--` on those types (the "bits" programs, in all three modes); locals, `if`/`else` and early `return`; and string `Length`, `+`, `Contains`, `StartsWith` and `==`. Building it found four translation bugs, now fixed and each kept as a regression test in `TranslationValidationRegressions`: `/` and `%` rounded like SMT-LIB instead of truncating toward zero like C#; under `[CheckedArithmetic]` a zero divisor and `MinValue / -1` were not checked; `Math.Abs` on a `long` under `[CheckedArithmetic]` was a Z3 sort error; and `%` on `decimal` was wrong.
  - **Not covered:** loops, calls, collections, records, nullable values, enums, calendar types, casts between other types, other string methods, `checked(...)` expressions, and contracts other than a pinned result. Each run checks one concrete path, so it tests what the formulas mean, not how Z3 copes with unknown inputs.
  - **Integer overflow is not a gap.** It was one until #35: without `[CheckedArithmetic]`, `int` and `long` were unbounded integers, so wrap-around and the `OverflowException` of `MinValue / -1` and `Math.Abs(MinValue)` were not seen. Now `[Verifiable]` code is sound by default: `int`, `uint`, `long` and `ulong` arithmetic is checked for overflow unless the code is in an `unchecked(...)` context or an `[UncheckedArithmetic]` scope, where it wraps and the wrapped value is what the prover reasons about. Inputs of an integer type are assumed to be in the range of that type; a string's `Length` is not given an upper bound beyond `int.MaxValue`, so `s.Length + 1` still needs a guard.
  - **Known gaps, left open:** `decimal`, `double` and `float` are exact real numbers, so `1m / 3m` is not rounded as in C#. The test `KnownGap_DecimalDivisionDoesNotRound` pins this down.
  - **The break-it corpus** (`tests/Verifiable.Analyzers.Tests/Soundness/Corpus`) holds hand-written programs that try to catch the analyzer out, each marked as one it must reject or prove. A rejected program carries a witness call that is run with its contracts checked at run time, so every entry is really wrong. Every method the analyzer accepts is also run on GalaxyCheck inputs, so a false proof can show up without anyone predicting it. Bugs it finds that are not fixed yet are marked `@known-bug`: the test passes while the bug is there and fails once it is fixed. See the corpus README.
- **Choosing what to check.** Every `[Verifiable]` method is lowered, and `CheckSelectionKernel.Select` (proved, above) passes over a method in silence only when lowering finished and found no obligation. If lowering stops at code it cannot translate, the method is reported with `VER101`: an error when it has contracts or obligations, a warning when it has neither. What is still trusted is the lowerer itself: it decides which obligations a method has, and an obligation it never creates is never checked. `LeadingContractBlock` decides which `Spec.Requires` calls are preconditions (only those at the top of the method); the analyzer reports any other one as `VER101` rather than dropping it silently.
- **The query CLI script.** `QueryEngine.BuildNamedQueryScript` loops over the path conditions and the `--assume` premise and writes each with `SolverPlumbingKernel.NamedAssertion`, then ends with `ProofKernel.NamedNegatedGoal`. The order and the labels are utility code. A label must never equal a declared name: Z3 accepts the clash, and later formulas then read the name as the label (true or false, as 1 or 0). Labels (`path_cond_N`, `assume_result_N`, `p_N_Kind`, `query_negated_goal`) use prefixes that no parameter (`p_` plus the escaped C# name) or local (`ssa_N_...`) can produce.
- **The `VER007` statement walk.** The rules for what a statement does to a token, and the check at exit, are in the core (`LinearTransfer`). Finding the statements is not: `LinearObligationAnalyzer` decides which operations count as a consumption, a move, a read, a discard or an overwrite, and handles variables that have no state yet. It also decides which paths exist. A `finally` block is analyzed once for each way of reaching it (falling out of the try, each `return`, `break` or `continue` that leaves it, and an exception). A `catch` block, and a `finally` reached by an exception, start from the join of the states at each point in the try body where something could throw, without the try's own locals; a token passed to a sink counts as consumed even if the sink then throws. A token has to travel in locals and parameters: passing it to a method that is not `[ConsumesObligation]`, or putting it in an array, tuple, `Nullable<T>`, field or collection, is rejected, because the analyzer cannot follow the copy. An async sink counts only if its task is awaited or returned. A local function's effect on the tokens it captures is summarised and applied at each call. The worklist's visit budget comes from the rank lemmas (plus the one extra flag above); going past it is an analyzer failure, not a pass.
- **The Z3 process plumbing** (`Z3SolverRunner`) sends the query and returns the output lines it read. Each read ends at a sentinel that carries a fresh random nonce, so no model value can end a read early, even one that spells a sentinel's text. The cache key's layout comes from the core (`CacheKeyMaterial`); collecting its parts (`Z3Identity`, the timeout as decimal text) and hashing it are utility. The hash covers the UTF-16 code units directly, because UTF-8 would map every unpaired surrogate to the same bytes. Counterexample parsing (`ParseModel`) reads `""` as the only escape inside a string, as SMT-LIB 2.6 does; it can produce a wrong counterexample, not a wrong verdict.
- **Names in the SMT script.** C# identifiers are written with `SmtTypeSystem.SymbolPart`: ASCII letters, digits and `_` are kept, and every other code unit becomes `$` and four hex digits. This is one-to-one, so two C# names never share a symbol, and Z3 never sees a non-ASCII symbol. String literals are escaped by `ContractExpressionTranslator.EscapeSmtString` (`""` for a quote, `\u{...}` for a backslash and everything outside printable ASCII). Both are tested against hostile input (`SmtInjectionTests`), not proved.
- **Finding weakened proof checks.** `ProofSuppressionAuditor` collects the settings that `VER107` judges with `SuppressionKernel`. It reads `<NoWarn>`, `-nowarn` and rulesets from the compilation options, `dotnet_diagnostic.*.severity` from `.editorconfig` and `.globalconfig`, category and all-analyzer severities, `#pragma warning disable` and `[SuppressMessage]`. It only checks projects with `[Verifiable]` code, and file-level settings only in files that declare it. It has limits:
  - `VER107` can be switched off like any diagnostic: `<NoWarn>VER107</NoWarn>`, `dotnet_diagnostic.VER107.severity = none`, `dotnet_analyzer_diagnostic.severity = none`, or an `[assembly: SuppressMessage]` with no target. A pragma or member attribute that names `VER107` is reported without a source location, so it cannot hide its own report, but project-wide settings can.
  - `dotnet_diagnostic.VER107.severity = warning` is not reported: it has the same effect as `VerifiableAllowWeakenedProofs`, which is the supported way to ask for it.
  - `<WarningsNotAsErrors>` only stops a warning from being promoted to an error. It cannot lower the proof checks, which are errors already, so it is not reported.
  - It cannot see `<RunAnalyzers>false</RunAnalyzers>` or `<RunAnalyzersDuringBuild>false</RunAnalyzersDuringBuild>` (then no analyzer runs, so neither do the proofs), or a `DiagnosticSuppressor` in another analyzer package.
  - When several settings apply to one ID, a weakening one can be reported even if another overrides it. The exception: an ID-specific setting is known to win over a category or all-analyzer setting.
- **The disk cache** (`SignedAnswerCache`) signs each entry with a per-user key, binding it to its query. The folder is built owner-only before the key is written, and an existing folder or key that group or others could access, or that is a link, is never trusted. On Windows the folder is created with a protected ACL (nothing inherited) that grants full control only to you, SYSTEM and Administrators, and the key inherits it; an existing folder or key is trusted only if it is owned by one of those three, no ACL entry lets anyone else in, and it is not a reparse point. Anything else is moved aside and rebuilt. If the runtime lacks the Windows ACL API (for example .NET Framework), no disk cache is used. The ACL decision (`WindowsAcl`) is pure and tested on every OS. The cache is as safe as your user account: code running as you (or as root or an administrator) can still forge entries.

## Known gaps found while drawing this line

These are open, and are listed so they are not forgotten:

- **A second consumption after a partial one, in the kernel.** `MaybeLive` means "live on some path", and the kernel's `ConsumeEvent` still reports a double consumption only for a token consumed on every path (`TransferLaws.DoubleConsumeIsOnlySeenOnEveryPath` keeps that visible). `VER007` closes the gap outside the kernel: `LinearObligationAnalyzer` keeps one more flag per token, "may already have been consumed on some path", set by every consumption, cleared when the variable gets a new token, merged with "or". A consumption while the flag is set (after a branch that consumed it, on the second pass of a loop, or a second time on a sink method's own parameter) is reported as a possible double consumption. That flag is analyzer code, so it is trusted, not proved. Moving it into the kernel would need a new lattice state for "consumed on some path", with the lemmas that go with it.
- **Vacuous proofs on one path.** `VER105` checks the whole premise set, and each callee guarantee at the call that assumes it. Two cases are still open. The translation's internal axioms (decimal rounding, strings, collections, calendars) are only checked as part of the whole premise set: each guarantee is checked against the assumptions made before it, so a guarantee that clashes only with a later axiom on its path is missed. And when the whole-method check is undecided, the per-call checks are skipped (`VER106` is reported instead). Premise checks use a fixed Z3 work budget rather than a clock, so the undecided result is the same on every machine (a 10 s wall-clock backstop applies only on extremely slow machines). `verifiable-query` reports per-path vacuity through its unsat core.

## Rules for contributors

- Building the solution proves the kernel, so it needs Z3: run `scripts/install-z3.sh` (or `.ps1`) first. Without it the build stops with `VER104` in `Verifiable.Core`.
- Anything that decides a verdict from a solver answer belongs in `src/Verifiable.Core`.
- The core stays free of Roslyn, I/O, mutable state and exceptions (the `[Verifiable]` gatekeeper enforces this).
- Every core rule is a `Spec.Ensures` with a plain-English `because`. Prefer exact contracts (`r == ...`) over partial ones (`r.StartsWith(...)`): a partial contract can let extra text, such as an `(assert false)`, slip through.
- When you add a rule, add a matching break to `KernelSelfVerificationTests.KernelBugs` so we know the proof can fail, and a reference check to `Verifiable.Core.Tests` so it is also checked without the prover.
- A kernel change is proved by the frozen kernel, so do not promote in the same change. Once it is merged, promote it in its own pull request: `scripts/promote-bootstrap-kernel.sh` (or `.ps1`) first builds `Verifiable.Core` to prove the live kernel with the current frozen copy, then copies the live kernel into `src/Verifiable.Analyzers.Bootstrap/Kernel`. It refuses to promote a kernel that is not proved. Never edit the frozen copy by hand.
- The bootstrap compiles the live analyzer sources against the frozen kernel. A kernel file with no frozen copy yet (a new rule) is compiled in as it is, so analyzer code can use a new rule straight away; that new rule is proved only by itself until it is promoted, and its reference tests in `Verifiable.Core.Tests` are what check it independently. Changing the signature of an existing kernel member that the analyzer calls breaks `Verifiable.Analyzers.Bootstrap`: add the new member alongside, promote, then remove the old one. If you cannot split the change, run the promote script with `--no-proof` (`-NoProof`) and say in the pull request that this kernel was not proved by an earlier one.
